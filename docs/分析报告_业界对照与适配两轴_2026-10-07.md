## 0. 一句话结论（先看这条）

> 把 VESC 和 ODrive 翻完之后，**"跨厂商设备树"没有先例** ——
> **VESC 只 STM32，ODrive 只 STM32（`Board/` 里只有 v3 一个版本）**。
> 真正的"多厂商"是 **ChibiOS / Zephyr** 在下面扛（`ChibiOS/.../ports/` 目录结构的职责），**`hwconf` 之上完全不管芯片**。
> 所以本工程**不需要**为"多厂商"设计任何东西；**需要的是 `board/` 的 ops 抽象 + 电机辨识流程**。

## 1. VESC 实测

### 1.1 目录事实

| 项 | 实测 |
|---|---|
| `hwconf/` 子目录 | **23 个**：`BMESC` `ENNOID` `example` `flipsky` `flipsky_official` `floatwheel` `funginers` `ipm` `itr` `JetFleet` `kingmmodel` `luna` `makerbase` `makerx` `other` `reepas` `shaman` `stormcore` `teamtriforceuk` `trampa` `tronic` `Uboxx` `vesc` |
| 每个目录 | **2 个文件**：`hw_<name>.h`（+ 可选的 `hw_<name>_core.h`） |
| `hw_example.h` | **27 行** —— 极薄，基本只有版本 + 包含 |
| `hw_example_core.h` | **248 行** |
| `hw_example_core.c` | **250 行** |
| **★ 但真正限制平台的** | `ChibiOS_3.0.5/os/hal/ports/` = **只有 `common` 和 `STM32` 两个** |

> **【事实】** `hwconf/` 看着"23 厂商"，但那是**第三方板卡厂商**（都基于 STM32）。
> 芯片维度上，**VESC 只有 STM32 一条路**（`ChibiOS ports` 里没有别的）。

### 1.2 怎么选板：构建期文本注入

```
Makefile:18   ALL_BOARD_NAMES = $(notdir $(wildcard hwconf/*))
Makefile:166  -DHW_SOURCE=hwconf/$(HW_SOURCE)  -DHW_HEADER=...
conf_general.h:34  #ifndef HW_SOURCE
conf_general.h:35  #error "No hardware source file set"
conf_general.h:37  #ifndef HW_HEADER
conf_general.h:38  #error "No hardware header file set"
```

> **【事实】** 选板 = **编译命令行两个 `-D`**（`HW_SOURCE` / `HW_HEADER`），
> 头文件里 `#include HW_HEADER` 文本包含。**没有运行时选板、没有注册表。**
> → **这与本工程"按板编译"的结论完全一致**（`.clinerules/30` 的伪 DT 约束 2「零解析」，被业界验证）。

### 1.3 一个头文件里混编四类东西

`hw_example_core.h` 实测混了四种：

| 类别 | 例 | 我们的对应 |
|---|---|---|
| **标识** | `HW_NAME` / `HW_MAJOR` / `HW_MINOR` | desc 的 `name` 字段 |
| **能力宏** | `HW_HAS_DRV8301` / `HW_HAS_3_SHUNTS` / `HW_HAS_PHASE_FILTERS` / `HW_HAS_PHASE_SHUNTS` | `ctx.hw_flags` **位** |
| **脚位** | `PHASE_FILTER_GPIO` / `PHASE_FILTER_PIN` / `LED_GREEN_GPIO` / `LED_GREEN_PIN` | desc 字段 |
| **★ 动作** | `ENABLE_GATE()` / `DISABLE_GATE()` / `IS_DRV_FAULT()` | **ops 函数** |

> **【判断】** 第 4 类（**动作**）是**我们对 VESC 最该吸取的一条**：
> **动作必须进 `ops`，不能靠宏**。本工程 `pwm_port_ops` / `adc_foc_port` 已经是这个形状 ✅。

### 1.4 两条反面教材（我们**不**学）

| # | VESC 的做法 | 为什么是反面 |
|---|---|---|
| **1** | `#ifdef HW_...` 散落在**业务代码**里 | 芯片/板卡判断**扩散到算法层** —— 正是 `.clinerules/30` 要挡的 |
| **2** | `QMLUI_SOURCE_HW`（UI 层也放硬件描述） | **描述耦合到展示层** |

### 1.5 单测：只测纯函数

```
tests/ : angles / float_serialization / overvoltage_fault / packet_recovery / uavcan_vesc_frames / utils_math
make/unittest.mk
```

> **【事实】** VESC 的测试**全部是纯函数**（角度数学、序列化、故障判定、包恢复），
> **没有一条测硬件路径**。
> → **【启示】** 本工程的单测也应该从 **`motor/` 纯算法**开始（`foc_svpwm` 的扇区/占空比数学、`emf_pll` 的 PI、Clarke/Park），**别一开始就测 HAL 链**。

## 2. ODrive 实测

### 2.1 目录事实

| 项 | 实测 |
|---|---|
| **`Board/`** | **只有 `v3`** 一个版本 |
| `board.cpp` | **593 行** |
| 选板 | **`Odrive.ioc`** —— **用 CubeMX** |
| 芯片库 | `ThirdParty/` = `CMSIS` / `FreeRTOS` / `STM32F4xx_HAL_Driver` / `STM32_USB_Device_Library` ← **只有 STM32** |
| `Drivers/STM32/` | `stm32_gpio.c` / `stm32_system.c` / `stm32_nvm.c` / `stm32_spi_arbiter.cpp` / `stm32_timer.c` ← **自带一层薄封装** |
| 构建 | `Tupfile.lua` **硬编码** `Drivers/STM32/` |
| 接口 IDL | `odrive-interface.yaml` **1741 行**；`interface_generator_stub.py` **13 行** |
| 算法层 | `MotorControl/`：`component.hpp` / `axis` / `controller` / `encoder` / `motor` / `foc` / `nvm_config` / `acim_estimator` / `oscilloscope` / `endstop` / `mechanical_brake` / `open_loop_controller` |
| 测试 | `Tests/`：`test_can` / `test_rotate` / `test_runner` / `test_timer` / `test_trap_traj` |

> **【事实】** ODrive **和本工程用的是同一套东西**：**CubeMX 生成 + HAL + `Odrive.ioc`**。
> **【事实】** ODrive 的"适配层"不是设备树，而是 **`Drivers/STM32/` 这 5 个文件**（gpio / system / nvm / spi_arbiter / timer）。
> → **【判断】** 这正好支持本工程的 **`platform/` backend** 思路 ✅ —— **业界头部项目也是"每个外设一族一个 backend 文件"，不是"通用设备树"。**

### 2.2 与我们最像的一处：CubeMX 与手写代码的边界

```
board.cpp:  #define ControlLoop__IRQHandler  OTG_HS_IRQHandler
board.cpp:  SystemClock_Config  —— extern "C"，实现放在 CubeMX 的 main.c
```

> **【事实】** ODrive 的做法是 **CubeMX 管"时钟与中断向量"，手写 `board.cpp` 管"绑定"**。
> **【判断】** 这与本工程 `.clinerules/40`（生成文件不写业务）**同源**；
> 差别在**它把手写绑定放在 `Board/board.cpp` 一个文件里**，本工程放在 `board/` + `config/bridge_*`。
> → **两种都能用；本工程更分散，但更干净**（生成物与业务物理分离）。

### 2.3 ODrive 有、我们缺的两个诊断件

| 件 | 位置 | 我们 |
|---|---|---|
| **栈高水位统计** | `main.cpp` 各线程 `stack high water mark` | ❌ 无 |
| **`vApplicationStackOverflowHook`** | `main.cpp` | ❌ 无（`FreeRTOSConfig.h` 的 `configCHECK_FOR_STACK_OVERFLOW` 未开） |
| CAN 线程句柄 | `odrv.can_.thread_id_` | ❌ 无（本工程 CAN 未接线） |

> **【判断】** 这两件**成本极低、价值明确**，且**归 CubeMX 侧**（见 `规划 §11`）—— 主人手动开一下即可。

## 3. 结论：适配分四层，业界只做到 L3

| 层 | 换什么 | 要改什么 | 业界（VESC/ODrive） | 本工程 |
|---|---|---|---|---|
| **L1** | 同 MCU、同外设类型，**换板** | **只改描述数据** | VESC：换 `hwconf/xxx` 头 | ✅ `board/*` 数据 |
| **L2** | 同 MCU，**换外设类型**（TIM→HRTIM） | 新写 backend + 改描述 | VESC：改 `ChibiOS` 配置 / ODrive：改 `Drivers/STM32/*` | 需新写 `platform/*_hrtim.c` |
| **L3** | **换 MCU 厂商** | 换 port 实现 | **都只 STM32，没有先例** | 有契约、无第二实现 |
| **L4** | **换电机**（跨机型） | **辨识流程 + NVM 写回** | VESC：`detect_*` 流程；ODrive：`acim_estimator` | ⚠️ **缺 NVM 段**（见 §5） |

> **【判断】** **L1~L2 是"表"能解决的；L4 是"流程"才能解决的。**
> 本工程硬件那条轴（L1~L3）已经有雏形；**电机那条轴（L4）几乎空白** —— 这才是"两条适配轴"里更欠的一条。

## 4. RTOS 与 CAN 接线：业界怎么切（本工程 CAN 未接线）

### 4.1 VESC 实测（`comm/comm_can.c`）

| 项 | 实测 |
|---|---|
| **ISR 里做什么** | **只收 + 入队**（`chEvtRegister(&HW_CAN_DEV.rxfull_event, ...)`） |
| 消费 | 独立线程 `chEvtWaitAnyTimeout(ALL_EVENTS, MS2ST(10))` + `canReceive(..., TIME_IMMEDIATE)` |
| 线程工作区 | **5 个**，都放 `.ram4`：`read 256` / `process 2048` / `status 512` / `status_2 512` / `status_internal 512` |
| 锁 | `can_mtx` + `can_rx_mtx`（**2 个 mutex**） |
| 备注 | `TIME_IMMEDIATE` → **收到就返回，不阻塞**（ISR 安全） |

### 4.2 ODrive 实测（`main.cpp`）

| 项 | 实测 |
|---|---|
| 线程 | `usb_thread` / `uart_thread` / `analog_thread` / `defaultTaskHandle` / `odrv.can_.thread_id_` |
| 诊断 | 各线程 **栈高水位统计** + `vApplicationStackOverflowHook` |

### 4.3 【判断】**ISR 三判据**（本工程 CAN 若接线，照这三条验）

| # | 判据 | 为什么 |
|---|---|---|
| **1** | **ISR 里只做"收 + 入队"**，不做解析/不做 FOC | 20 kHz JEOC 链已经是硬实时的最坏情况；CAN ISR 不能抢它 |
| **2** | **队列必须够长或有丢包策略** | 快速帧率下 256 B 工作区会满（VESC 用 2048 给 process） |
| **3** | **共享量用 mutex 或单写者** | VESC 用 2 个 mutex；本工程 FOC 在 ISR、CAN 在线程 → **必然跨上下文** |

> **【事实】** 两家**完全一致**：**FOC 在 ISR，CAN 走线程**。
> → **【判断】** 本工程的 `COMMUNICATION_FDCAN` 若接线，**FreeRTOS 够用**；
> 缺的不是 RTOS，是 **① 线程栈大小没测（无高水位）② `configCHECK_FOR_STACK_OVERFLOW` 未开 ③ heap 3072 可能偏小**。
> 这三件**都在 CubeMX 侧**（见 `规划 §11`）。

## 5. 两条适配轴（硬件 = 表 / 电机 = 流程）

### 5.1 两条轴的性质完全不同

| | **硬件适配轴** | **电机适配轴** |
|---|---|---|
| 变化对象 | 板卡 / 外设 / MCU | 电机机型 |
| 变化频率 | 换板才变（**月/年**） | 换电机就变（**周/月**） |
| 谁能做 | **编译期常量表** | **只能跑流程测出来** |
| 产物 | const desc + ops | **辨识结果 → NVM → 参数** |
| 我们现状 | L1~L2 雏形有 | ❌ **几乎空白** |

### 5.2 电机参数的"可整定性"分档（决定哪些必须辨识、哪些能解析算）

| 档 | 参数 | 怎么来 |
|---|---|---|
| **A. 铭牌直接给** | 极对数、额定电流、Kt | 人工填 / 手册 |
| **B. 万用表可测** | `Rs`（相电阻）、`Ld/Lq`（低频） | 简单测量或辨识 |
| **C. 需辨识流程** | `ψf`（磁链）、`Ld/Lq`（高频差异） | **必须跑辨识** |
| **D. 需运行整定** | 电流环 PI、速度环 PI、观测器增益 | **可由 B/C 解析算出**（见 5.3） |

### 5.3 一个被低估的红利：**电流环 PI 可以解析整定**

> 有了 `Rs` / `Ld` / `Lq` 和带宽目标，**电流环 PI 是解析可算的**（`Kp = ωc·L`，`Ki = ωc·R`），
> **不需要试凑**。
> → **【判断】** 本工程已有 `rs_ident` / `ld_lq_ident` / `ident_flow`，
> **缺的是"辨识完自动算出 PI 并写回"这一步**。这是 J3 的核心价值。

### 5.4 依赖方向：**轴 B 依赖轴 A**

```
辨识流程（轴 B）  ──需要知道的是哪台电机/怎么采样──▶  电机铭牌 + ADC 标定（轴 A）
```

> **【判断】** **先有硬件表（轴 A），电机流程（轴 B）才有落脚点** —— 但两者**不冲突、可并行**。

## 6. 一个硬发现：`factory_nvm` **没有电机参数段**

| 项 | 实测 |
|---|---|
| `cal/factory_nvm.h` 现有段 | 编码器标定（±offset / 方向）、**电机相序绑定** |
| **电机参数段**（Rs / Ld / Lq / ψf） | ❌ **不存在** |
| 后果 | `rs_ident` / `ld_lq_ident` 的结果**只能人工回填宏**，重新编译 |

> **【事实】** 电机辨识结果**目前进不了 NVM** → **换电机 = 改宏 + 重编译**，不是"跑一遍流程"。
> → **【判断】** 这是 **J3（电机适配一条命令）当前最大的拦路石**；
> 也是 **`memory_map` / NVM 布局** 这件事**真正有价值的理由**（比"防撞段"实在得多）。
> （原稿说 `memory_map`「真价值在 OTA」—— **应更正为：真价值在 NVM 分区与电机参数段**。）

## 7. 对本工程的启示（汇总）

| # | 启示 | 依据 | 落到哪 |
|---|---|---|---|
| 1 | **不为"多厂商"设计任何东西** | VESC/ODrive **都只 STM32** | 规划 §7 红线 |
| 2 | **动作进 `ops`，数据进 `desc`** | VESC 把 `ENABLE_GATE()` 宏塞进 desc 头 | 已符合 ✅ |
| 3 | **选板 = 编译期 `-D`，零运行时解析** | VESC `HW_SOURCE`/`HW_HEADER` | 伪 DT 约束 2 ✅ 被验证 |
| 4 | **单测从 `motor/` 纯算法开始** | VESC 测试全为纯函数 | `tests/`（未建） |
| 5 | **FOC 在 ISR、CAN 走线程** | 两家一致 | 接线时照抄 |
| 6 | **栈高水位 + 溢出 hook 必须有** | ODrive `main.cpp` | **CubeMX 侧**（规划 §11） |
| 7 | **电机轴要"辨识 → 算 PI → 写 NVM"** | ODrive `acim_estimator` | **J3**，需先补 NVM 段 |
| 8 | **`platform/` 一族一个 backend，不做通用设备树** | ODrive `Drivers/STM32/` 5 文件 | 本工程已经是 ✅ |

> **一句话**：**VESC/ODrive 用事实证明了两件事** ——
> **① 「每外设一族一个 backend + 编译期描述表」是对的（不需要通用设备树）；**
> **② 「换电机」只能靠辨识流程 + NVM，光有描述表不够。**
