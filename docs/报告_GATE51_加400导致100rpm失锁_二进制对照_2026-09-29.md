# 报告：GATE51「只到 300 正常 / 编进 400 就在 100 rpm 失锁」——二进制对照（2026-09-29）

**对象**：`M1_HFI_GATE=51`（S2i：Park=θ̂，速度环吃编码器，ch8=PLL 积分）  
**对照包**：  
- **1948**：只到 300 → 100 rpm **正常**（锁回 ~0.4 s，err≈−5°，Iq≈0.26 A）  
- **1942**：编进 400 → 仍指令 100 rpm，但 **θ̂≈−90°、Iq 顶满、轴约 22 次/s 正反抽**  
**现行固件**：已改回只到 300（Code=56276），与 1948 同档。

---

## 0. 一句话

> **不是 Flash 装不下，也不是 MCU 卡死，更不是 400 rpm「转不动」。**  
> 源码只多了一档 400；编译后整图只多 **24 字节**。PLL 热路径机器码不变；变的是转速指令函数被编译器重写。  
> 台架上却在 **尚未跑到 400 的 100 rpm** 就失锁——问题落在「加档改变了前两档所在函数的代码生成」，不是 400 工况本身。

---

## 1. 现象（CSV）

| 项 | 1948（只到 300） | 1942（编进 400） |
|----|------------------|------------------|
| 前 20 s 指令 | 100 | 100（未到 400） |
| 编码器转速 | ≈99.9 | ≈33，std≈126 |
| PLL 积分转速 | ≈100 | ≈0 |
| θ_err | ≈−5°，多数 \|err\|&lt;15° | ≈−95°，几乎全程失锁 |
| Iq | ≈0.26 A | 中位 ~7.6 A，抖时钉满 |
| 轴正反抽 | ≈0 | ~22 次/s |

1948 在 25 s 已切 200 且跟随正常；录到 ~27 s 停，300 档未跑完，但 **100 rpm 对照已足够**。

「卡死」的观感 = 轴剧烈正反抽 + 电流顶满，**不是** HardFault / 看门狗停转；控制环仍在跑，只是 Park=θ̂ 已指到错误轴。

---

## 2. 源码上到底差了什么

只到 300（现行）与「加 400」相对差：

1. profile：`M1_HFI_RUN_RPM4=400`，`M1_HFI_RUN_RPM4_S=20`  
2. `hfi_run_total_s()`：60 s → 80 s（只决定何时 DONE）  
3. `hfi_run_speed_ref_ext()`：多一个 `if` 返回 400  

**没有**改：Park、PLL 增益、W_MAX、速度环反馈、电流限、注入、XY、A_cmd。

前 20 s 两条路径的 C 语义都是 `return 100`。`run_total` 变 80 在 t≈0 时也与 60 一样「未到期」。

---

## 3. 二进制上到底差了什么（A/B 实编）

本机对同一树先后编「只到 300」与「+400」，`fromelf` 对照：

| 项 | 只到 300 (A) | +400 (B) | 含义 |
|----|--------------|----------|------|
| Program Code | **56276** | **56300** | **+24 B**，与「代码太大」无关 |
| `hfi_sqwave_on_current` | 相同 | 相同 | **解调 / PLL 热路径未动** |
| `hfi_sqwave_on_angle` | `run_total` 常量 **60** | 常量 **80** | 前 60 s 行为不应变 |
| `hfi_sqwave_get_speed_ref_rpm` | 100/200 + 表查 300 | **整函数被重写**；表多 400；100/200 段换了浮点寄存器安排 | 真正可见的控制流代码差 |

要点：

1. 源码里即便把 100/200 和 300/400 拆成 `s2d` / `ext` 两个 `static` 函数，**ArmClang 仍会内联**进 `get_speed_ref`，用交错的 `VCMPE` + `IT` 做档位表。  
2. 加一档 400 后，编译器重排该函数（寄存器从「t 在 s2」变成「t 在 s6」等），并加长字面量表。  
3. 按反汇编推演，B 在 t&lt;20 时仍应返回 100——与 1942 的 **wref 仍停在 100** 一致。  
4. 因此：**失锁时指令并没有错成 400**；差的是「同一条取指令函数的机器码形态」，外加整图地址整体后移约二十四字节。

---

## 4. 排除项（已否定）

| 猜测 | 结论 |
|------|------|
| Flash / 代码体积不够 | 否。整图只 +24 B |
| RUN 总时长太长（60→80） | 否。100 rpm 在 RUN 第 0 秒，碰不到 DONE |
| 400 rpm 步进太难 | 否。1942 从未进入 400；卡在第一档 |
| 加 400 改了另一套 PLL/Park | 否。`on_current` 机器码不变 |
| MCU 死机 | 否。遥测连续，属失锁振荡 |

---

## 5. 还没钉死的因果

已钉死：**相关变量 =「是否把 RPM4 编进固件」**；**无关变量 = 400 rpm 工况本身、总时长、代码体积**。

尚未钉死到单条汇编：为何「返回值仍是 100、PLL 函数未改」时，θ̂ 仍会塌到 −90°。候选（按优先级）：

1. `get_speed_ref` 浮点比较调度 / 寄存器重排的**代码生成副作用**（每次 FOC 都调用）；  
2. +24 B 引起的后续函数布局变化（目前无证据指向绝对地址写死）；  
3. 台架偶发与编 400 碰巧同批次（1948 回退可复现「正常」，削弱此项）。

---

## 6. 建议下一步（加档方式）

不要再在浮点 `if (t < …)` 链上堆 400/500/…。

改为例如：

- `static const float k_rpm[] = {100,200,300,400,…}`  
- 整数毫秒或 `idx = (int)(t / step_s)` 查表  

目标：**加一档只多几个字面量，不改前两档的机器码**（可用 A/B `fromelf` 验：`get_speed_ref` 前半段哈希不变）。

在改表法之前，保持 GATE51 **只到 300** 作基线；需要复现 1942 时再临时加回 RPM4。

## 8. 给对话用的白话版

**加 400 并不是「多跑一段更难的速度」把电机搞挂了，而是「多编进这一档」让编译器把取转速指令的那一小段函数重新抠了一遍。**  
整固件只胖了 24 字节；真正算角度的 PLL 代码一行机器码都没变；指令在 100 rpm 时也还是 100。  
但 1942 就是在这个「指令仍是 100」的阶段，角度掉到反轴、电流顶满、轴正反抽。  
所以这是**联编/代码生成问题**，不是 400 rpm 控制律问题；下一步要用查表做阶梯，避免再触发这类重编译。
