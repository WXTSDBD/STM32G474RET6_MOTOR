## §1 为什么需要它

`config/motor_params_m1.h` 实测 **3378 物理行 / 1004 个 `#define`（含 include guard；唯一名 592）**。

`规划_架构改进` §7 红线第 3 条已定：

> ❌「删大量宏定义」—— 删宏不产能力；85 个 `#error` 是资产。
> **只搬两类**：铭牌 + 实验开关 → 数据结构。

但"**搬哪几个、搬了要动多少处**"目前没有依据。已有的教训：

- **R1a**：为归一 `3999`，才发现它有 **4 处真相源**，还留下一个"看着像 `arr/2`、其实不是"的 `PHASE_PWM_CENTER`
  —— 这些是**人眼一行行读出来的**。
- 3225 行 × 1004 个宏，**人眼读不完，也读不准**。

**所以**：让"搬哪些宏"从一个**感觉问题**，变成一个**有数字支撑的决定**。

## §2 表长什么样（列定义）

| 列 | 含义 |
|---|---|
| `name` | 宏名 |
| `line` | 定义行号 |
| `class` | 归属：**铭牌 / 参数 / 能力 / 策略 / 实验 / 工具** |
| `def_kind` | 定义方式：裸 `#define` / `#ifndef` 守卫 / `#undef`+`#define` |
| `undef_in` | `#undef` 出现位置：`param`（本文件内）/ `profile` / 无 |
| `macro_deps` | 宏值里引用的其他宏（正向依赖） |
| `depended_by` | 哪些宏的值引用了我（反向；搬迁断编译期计算） |
| `reads` | 读取点（`文件:行`） |
| `read_file_n` | 被几个文件读 |
| `hot_path` | 是否有读取点落在热路径文件 |
| `profile_override` | 是否被 profile 通过 `#undef` 覆盖 |

## §4 两行真实样例（为什么必须靠表）

### 样例 A · `M1_RS_OHM`（看起来最像"铭牌"，理应最好搬）

| 项 | 实测 | 问题 |
|---|---|---|
| 定义 | `motor_params_m1.h:42` `#define M1_RS_OHM 0.122f` | **裸 `#define`，无 `#ifndef`** |
| 能否被 profile 覆盖 | ❌ 不能 | 但文件头写"profile 可覆盖" → **对铭牌块不成立** |
| 宏依赖 | `:780` `M1_PI_KI_NOMINAL (M1_RS_OHM * M1_PI_WC_RADS * M1_CTRL_TS_S)` | 搬进结构体 → **编译期计算消失** |
| 读取点 | `deadband_id_cal.c:716/766`、`ld_lq_ident.c:940`、`rs_ident.c:81`、**`motor_foc_loop.c:174`** | 最后一处在 **FOC 热路径** |

⇒ **搬它不是改 1 行**：要处理依赖链 + 热路径"立即数 → 内存读" + 碰 4 个文件。

### 样例 B · `M1_OUTER_THETA_FB_SRC`（看起来像"参数"，其实是策略轴）

| 项 | 实测 |
|---|---|
| 定义 | `:265` **`#ifndef` + `#define 0`** → ✅ 可覆盖 |
| 覆盖 | 两个 profile 用 `#undef`+`#define` 强制：`m1_sensed_pos_mit:123`→0、`m1_sensorless_pos_mit:280`→2 |
| 读取 | **全在 `#if` 里**：`motor_current.c:176 / :689 / :691 / :927 / :1118 / :1486 / :1775` |
| 真实归类 | ❌ **不是参数，是策略轴** → 要运行时化，得把 ~8 处 `#if` 改成 `if`，**且在热路径** |

⇒ **"看起来像" ≠ "就是"。**

## §5 ★ 核心发现：`#undef` 必须分两类，不能一刀砍

实测：`#undef` 共 **758 处**（本文件内 182 + profile 内 576）。**两类含义完全不同**：

| `#undef` 位置 | 数量 | 含义 | 处置 |
|---|---|---|---|
| **`profiles/*.profile.h`** | **576** | **合法覆盖**：`#ifndef` 挡着，要覆盖**必须先 `#undef`** | ✅ **全部保留** |
| **`motor_params_m1.h` 内** | **182** | **强制写死**：破坏"profile 可覆盖"契约，且**语义依赖 include 顺序** | ⚠️ **这才是收口对象**（且须逐个分类后再动） |

> ⚠️ **修正此前口径**：`规划 §5.0` / 本方案早期表述里的"**收口 182 处 `#undef`**"是**粗暴的**。
> 正确做法：**先把 182 处逐个归类**（"确实要强制" / "其实是重复定义" / "写错了"），**再决定删或留**。
> **这 182 处正是"某个值是多少"依赖 include 顺序的根源。**

## §7 用途（5 个）

1. **决定第一刀搬谁** —— 挑"读取点少 + 不在热路径 + 无 `#undef` + 不参与宏计算"的子集，**不靠感觉**。
2. **算改动面** —— 先知道是"改 4 个文件 9 行"还是"改 30 个文件"，**再决定一刀切多大**。
3. **给 `#undef` 收口提供名单** —— 分清 182 处哪些能删、哪些必须留。
4. ★ **搬迁验收（最实用）** —— 搬完再跑一次，`diff` 两份 json → **自动查出"哪个宏漏搬 / 哪个读取点没改"**。
   这比人眼残留扫描可靠（`R1a` 那次"自研目录已无 `voltage_power_supply`"就是靠人眼扫的）。
5. **给实验框架定位置** —— 以后新增一个旋钮，**查表就知道它该进 `motor_cfg_t` / `atrb` / profile / 段表**，不必每次重新讨论一遍。

## §8 不做什么（诚实边界）

| 不做 | 说明 |
|---|---|
| ❌ 不产生能力 | 它是一张**账**，不是功能 |
| ❌ 不让文件变小 | `motor_params_m1.h` 仍 **3225 行**，宏数仍 ~1004 |
| ❌ 不替人拍板 | "搬哪些"仍是主人的决定 |
| ❌ 不是手写表 | 会过期 → **正确形态 = 可重复跑的脚本 + json 快照** |
| ❌ 不动热路径 | **只读** |
| ❌ 不删宏 | 红线：85 个 `#error` 是资产；**只搬**铭牌与实验开关两类 |
